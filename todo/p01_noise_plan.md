# P0.1 选择抗噪:修订方案(v2,跨域)

2026-07-26 重写。v1 的第一优先项被真实 run 数据证伪,证伪过程和原文保留在
文末附录 —— 那是"为什么当初选错"的记录,比结论本身更值得留。

**核心修正**:v1 把统计检验当解药。但 IMO 每 run 只有 12 道题、16 个候选,
**这个体量下没有任何假设检验有功效**。真正能动的两个杠杆是「终选别取最大值」
和「把压扁的度量摊平」,两者都不需要更多测量。

## 0. 实测事实(标注可信度)

| | IMO | modmul |
|---|---|---|
| 候选 | 确定性 agent(三模型温度全 0) | 训练一个模型 |
| 评估单元 | train 12 / val 12 / test 36 题 | ASHA 分档,3~10 层 × 30/40/50 例 |
| 重复评估 | 温度 0,残余抖动未测(§5) | **未测量**(见下) |
| 题目抽样噪声 | 理论 sd ≈ 0.14 | — |
| 典型世代效应 | ~0.05 | — |
| 已实测的失败 | **val 0.595 → test 0.389** | 无 run 数据 |
| 病因 | **终选在 12 题上取 max** | **度量把信号压扁 100 倍** |

⚠️ **v1 表里的 modmul「SNR≈1.8」已撤回**:那里的"效应量 0.0018"和"噪声
sd 0.0010"来自**同一组 3 次重复的同一个 seed**——效应就是噪声本身,自己
除自己。而且 `MODMUL_QUICK` 只有 5 例/层(分辨率 0.2),整个结论建立在
一个 case 翻转上。modmul 的噪声**目前是未测量状态**。

§4(度量压缩)不依赖这次测量 —— 它是对 `(h90+overall)/11` 的算术。

## 1. 终选改用悲观估计(先做,一处 `max` 的键)

**唯一被实测到的失败**是 val→test 落差。病灶在
[`experiments/imo_proof/evolution.py:428`](../experiments/imo_proof/evolution.py):

```python
selected = max(validation, key=lambda item: (item[1].points_percentage, ...))
```

top-3 候选各在 **12 题**上评一次,取点估计最大值。12 题的二项标准误
≈ √(p(1-p)/12) ≈ 0.14,而三者真实差距远小于此 —— 这是教科书级的幸运者
诅咒:**取最大值这个动作本身**就把噪声算进了得分。

### 改动

1. `Grade` / `EvalReport` 各加两个**带默认值**的字段:

```python
n_units: int = 0        # 评估单元数(题/例),0 = 域未上报
sem: float = 0.0        # fitness 的标准误,0 = 域未上报
```

带默认值 ⇒ 线上兼容:`coerce_grade` 多发两个键,老消费方忽略;
`EvalReport.from_json` 用 `.get` 兜底。不动 `WIRE_SCHEMA_VERSION`。

2. **sem 由域产出,不由 harness 猜**。这是 v1 的第二个错:harness 没有
   能力算它。
   - IMO:题级 bootstrap 或二项近似(温度 0 时重复评估 sem 恒 0,**只能**
     从题级来);
   - modmul:跨种子重训的散布;
   - 未上报的域:`sem=0` ⇒ LCB 退化成点估计,行为不变。

3. `Candidate.fitness_lcb = fitness - z * sem`(z=1,单边 ~84%;门槛低是
   故意的,见下)。

4. **两个场景分开用**:
   - **父代选择用点估计** —— 探索要乐观。压低高方差候选会掐死探索,这是
     和 imp@k 的 `max` 的真实矛盾,靠"分场景"化解,不靠二选一;
   - **终选 / best 追踪用 LCB** —— 承诺要悲观。

⚠️ **modmul 例外**:`h90` 是阶跃项,对称区间会误描述它。置信度要算在
**连续量(逐层精度)**上再传播过阈值(即"第 t 层 ≥0.9 的概率"),不能直接
给 fitness 套 ±。这也是 §3 存在的理由之一。

### 落地后的实测:**LCB 不换人**(2026-07-26)

代码已落地(505 测试绿,2 个是既有红)。拿三个历史 run 的真实 validation
产物回放选择:

```
e5s_r2            0.4524/sem .1405   0.3571/.1310   0.3690/.1286   → 同一个赢家
e5s_s0            0.5357/.1408       0.5119/.1412   0.3571/.1379   → 同一个赢家
imo_multi_island  0.5952/.1448       0.4405/.1298   0.3690/.1286   → 同一个赢家
```

**3/3 完全不换人。** 原因是结构性的:12 题的标准误几乎不随分数变化
(0.129–0.145),减一个近似常数不会重排序。**我犯了和 v1 同一类错误** ——
提出机制却没先验证它会触发。区别是这个改动**正确且无害**(不会像 v1 那样
把活机制改成死代码),且是 §4 的前置,所以保留,但要如实标注:
**当前近乎 inert。**

### 但回放暴露了真正的病灶:诅咒是**估计偏高**,不是**选错人**

```
run                val 均值   val 赢家   诅咒偏高   test     总落差
e5s_r2             0.3929    0.4524    +0.0595   0.3611   -0.0913
e5s_s0             0.4683    0.5357    +0.0675   0.3770   -0.1587
imo_multi_island   0.4683    0.5952    +0.1270   0.3889   -0.2063
```

3 个候选取最大值带来的偏高是 **0.06–0.13**,占了总落差的 **50–65%**。
剩下的 0.03–0.08 落在 test 自身的 sem(0.076)量级内,分不清是划分难度差
还是噪声。

**结论重写**:val→test 落差**大部分不是 bug**,是"取最大值"的必然偏差 ——
而 LCB 修不了它,因为 LCB 不重排序。真正该改的是**汇报口径**:

1. summary 里"selected 的 validation 分"必须标为**有偏高估**,不能当作
   该程序的质量估计对外引用(`points_lcb` 已一并落盘);
2. 要把诅咒和划分难度分开,只需**一次额外 test 评估**:把一个**没被选中**
   的 finalist 也评一遍 test。它的 val 分没有被取最大值,所以 val−test
   之差就是纯划分难度项。**这是整份计划里最便宜的一个决定性实验。**

## 2. modmul 度量重设计(第二做,纯算术,无需测量)

`_fitness = (h90 + overall) / 11`([grade.py:548](../experiments/modmul/grade.py)):

- 某层精度翻倍(0.2→0.4)→ fitness **+0.0018**;
- 跨过某层 0.9 → **+0.091**(50 倍)。

地形 = **几乎全平 + 偶尔悬崖**。对演化搜索是最差形状之一:选择压力全靠
悬崖,悬崖之间无坡可爬,而爬坡正是变异唯一能提供的东西。

两个方向(择一,需单独 A/B):

- **选择用 `overall_accuracy`(连续),`h90` 只进终评报告** —— 排行榜口径
  不变,只是不再拿它当搜索信号;
- 或**软化**:`Σ_t sigmoid((acc_t - 0.9)/τ)`,保留"跨阈值有奖励"的语义
  但给出梯度。

只动 `experiments/modmul/grade.py`,属域内决策,不动 harness。

## 3. 配对向量:降级为描述,不做检验

**v1 在这里错得最实**。全部真实父子对(e5s_r2 14 对 + e3r_r2 7 对,
n_items=12):

```
最大不一致数 = 2   →   双侧符号检验最小可能 p = 0.500
```

12 题要 **5 题同向翻转**才到 p<0.1、**6 题**才到 0.05 —— 那是 42% 的绝对
分差。**21 对里没有一对能触发**。按 v1 实施,反思器会把 100% 判成 noise,
`RegressionSoftPenalty` 的连败**永远清零** —— 把一个正在工作的机制改成
死代码。正是 liveness-audit 那天挖出来的缺陷类型。

### 保留什么

配对的价值是**描述**不是**推断**。现在
[`reflection.py:339`](../evoharness/evoplus/reflection.py) 用
`parent_sig.hamming(child_sig)` —— 一个**对称**计数,分不清方向:

```
+1 -1  换了一题(纯搅动)      21 对里占 5 对
+0 -2  两题变差、无一变好      实打实的退步
```

标量 Δ 里这两者可能长得一样(partial credit 让 `+1 -1` 也能有正 Δ)。

**改动**:`BehaviorSignature` 加 `improved_over(other) -> (up, dn)`;
反思器渲染 `+{up} -{dn}`,noise 提示改为**直白规则**
(`up == dn` 且 `|Δ|` 小 ⇒ 提示 noise),替换掉 `|Δ| ≤ 1/n_items`
—— 后者是我在 IMO 语境下拍的,在 modmul 上 `n_items` 是被截断的反馈条数、
与计分无关。**不引入 p 值**。

`RegressionSoftPenalty` 的判据改为 `dn > up`(而非 `dn > 0`,也非显著性),
纯保留现有触发力度,只去掉搅动误判。

### 不做什么(v1 的第二个错)

**不把 `pass_vector` 放宽成 `tuple[float, ...]`**。理由:

1. **modmul 根本不满足配对前提**。ASHA 分档
   ([grade.py:83](../experiments/modmul/grade.py)):停在 R0 评 3 层、
   晋 R1 评 6 层、R2 评 10 层 —— **父子可能评的不是同一批题**;
   `items` 在 rung 循环里被逐档覆盖,只剩最后一档;
   `MAX_FEEDBACK_ITEMS_PER_TIER=20` 而实际计分 30/40/50 例,反馈向量是
   **前缀子采样**,重建不出 fitness 依赖的精度。
   于是向量长度 60/120/200 不等,而 `hamming()` 对长度差直接加
   `abs(len(a)-len(b))` —— 晋级失败的孩子凭空拿到 60 的距离。
2. **逐层精度不在 items 里,在 `visible_metrics` 里**。v1 说"放宽类型就能
   装下"是错的:那是**换数据源**,不是放宽类型。
3. **爆炸半径 v1 漏列**:`encode()` 是存进 run.db 的比特串(要迁移);
   `BehavioralNoveltyPolicy` 是第四个消费方(归档准入 + 去重),v1 只列了三个。

modmul 若要配对,正确单元是**父子都评过的那些层的精度**,在 tier 交集上
对齐 —— 独立于 `pass_vector`,等 modmul 有真实 run 数据后再设计。

## 4. 确认协议:IMO 已有,先别加抽象

v1 提的 `Confirmable` 协议,**IMO 那一半已经在跑**
([evolution.py:409-437](../experiments/imo_proof/evolution.py)):

```
train(12) 选 top-3  →  validation(12) 复评  →  argmax  →  test(36) 报告
```

这就是"在不相交的确认集上买第二意见"。缺的不是协议,是 §1 那个 `max`。

还有一处 v1 内部矛盾:现在只有 **12/12/36** 三个 split。若 run 中途的确认
吃掉 validation,终选就没有干净集了 —— 正是 v1 自己警告的"确认即过拟合"。

**所以顺序是**:先做 §1(用现有的 validation 复评 + LCB),观察是否还有
残余落差;只有当落差仍在、且定位到"训练集选择阶段就选错了",才值得加
run 中途的确认。届时:

```python
@runtime_checkable
class Confirmable(Protocol):
    def confirm(self, cand, workdir, attempt: int) -> EvalReport: ...
```

- **harness 决定**何时买(仅在候选声称刷新最优时 —— 幸运者诅咒只在取最大值
  时咬人)、怎么合并;
- **域决定**买什么(IMO:换题;modmul:换种子重训);
- 未实现的域退回当前行为。

**成本实测**:best-update 频率 `e5s_r2` 2/16 = **12%**,`e3r_r2` 3/9 = 33%
(后者是被杀掉的短 run,分母偏小)。区间 **12–33% 额外预算,不是 K 倍**。

## 5. 未测量项(不阻塞)

`scripts/measure_eval_noise.py`(IMO)首次运行因与主 run 争抢 provider 崩溃
—— **是我自己造成的**,已加重试 + 分段落盘。它量化的是温度 0 下的残余抖动,
只影响 §1 里 IMO 的 sem 是否需要加一个重复项;方向已定(题目抽样 sd≈0.14
压倒残余抖动),所以 sem **以题级 bootstrap 为主**。

`scripts/measure_modmul_noise.py` 需要**用完整 RUNGS 重跑**(非 QUICK),
否则 5 例/层的分辨率量不出任何东西。

两者都应在主 run 结束后补跑,不与实验争抢资源。

## 实施顺序(与 v1 相反)

| | 项 | 为什么在这个位置 |
|---|---|---|
| 1 | **§1 终选 LCB** | 一处 `max` 的键 + 两个带默认值的字段;直击唯一实测失败 |
| 2 | **§2 modmul 度量** | 纯算术、不等测量、可能比抗噪更重要;需单独 A/B |
| 3 | **§3 配对描述** | 小改;修掉搅动误判 + 拆掉 IMO 专属的 `1/n_items` |
| 4 | **§4 确认协议** | 只在 §1 之后仍有残余落差时才做 |

**验收**:每一项落地后跑 `scripts/audit.py`,确认新机制**真的在触发**
—— v1 的第一优先项如果照做,单元测试会全绿而机制永不触发。这正是
liveness audit 存在的理由。
