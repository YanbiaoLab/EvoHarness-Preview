## 1. 前置判断

§1.1–§1.3 是本文档的地基，改动它们等于换一份计划；§1.4–§1.6 是节点层的接线细节，
其中 §1.5 与 §1.6 各自承重。

### 1.1 走 Lean 版，不走自然语言版

`superhuman/imobench/` 里有两个容易混淆的 benchmark：

| | 判定 | 说明 |
| --- | --- | --- |
| IMO-ProofBench（`proofbench_v2.csv`） | 0–7 分评分细则，四档（Incorrect / Partial / Almost / Correct） | 判分靠人或自动评分器 |
| IMO-LeanProofBench（`lean_proof_bench_v2.csv`） | Lean 编译 + 公理检查，0/1 | 多一列 `Lean Statement`，Mathlib 4.27.0 |

**取后者。** 自然语言那一版的评估器是语言模型，把它放进有搜索压力的循环里，搜索
一定会朝它的盲区爬——那正是适应度最高的方向。Aletheia 在 700 道 Erdős 问题上的
数字是这条的实证：它自己的验证器筛出 212 份「可能正确」，数学家核完只剩 63 份技术
正确、13 份有数学意义；能明确判定的 200 份里 68.5% 是根本性错误。**那个验证器是
降低人类工作量的过滤器，不是判定程序**，而 Aletheia 后面站着一队数学家，我们没有。

顺带记一条防止误读的对照：Aletheia 在 ProofBench Advanced 上 93%，LEAP 在 Lean 版
Advanced 上 56.7%。**这两个数字不可比**——前者是人类专家给自然语言证明打分，后者
是 Lean 内核逐行验。

### 1.2 抄 LEAP 的骨架，不抄 Aletheia 的模式

LEAP 里已经装了 Aletheia 对我们有用的那一半：它的直接证路径和分解路径**都先过一个
非形式化的证明或蓝图**，再翻译成 Lean。区别只在判定权交给谁。

一句话原则，贯穿全文：**让语言模型判「这条路值不值得走」，不让它判「这个结果对不对」。**
LEAP 的分解审稿人和 Aletheia 的验证器架构上是同一个东西，差别是前者判搜索方向、
后者判正确性。前者判错只是浪费预算，后者判错就是把假结论当成真的。

### 1.3 两层基因，以及三种必须分开的「迭代」

> **v1 和 v2 各错一次，v3 一并更正。**
> **v1** 写「基因是证明器，不是证明」，据此让子目标求解走 `BasicSearchProfile`——
> 把节点层与脚手架层写成了二选一，这部分 v2 改对了。
> **v2** 引 LEAP Table 5 论证「跨候选世系有效、所以必须用 `EvolutionSearchProfile`」
> ——**这是归因错误**。Table 5 的 iterative 设置是「单个初始尝试 + 最多 20 次编译反馈
> 修订，得 Pass@1」，全部发生在**一条轨迹内部**，与多代候选、weighted parent、archive
> 无关。它不能证明需要 `EvolutionSearchProfile`。v3 把这一条降级为待验证假设，见 §1.6。

**两层基因，在图的上下两侧，互不冲突（v2 的这部分保留）：**

| 层 | 基因 | 在哪一步 |
| --- | --- | --- |
| **节点层** | 一份**证明**（攻某条引理的 `.lean`） | P-3、P-4、P-5 |
| **脚手架层** | 一个**证明器**（何时分解、审稿判据、预算分配…） | P-6 |

#### 三种「迭代」，本仓库里都叫 repair，必须分开记

混淆它们是 v2 出错的直接原因，也是 P-2 归因失效的直接原因：

| | 位置 | 是什么 | 谁开关 |
| --- | --- | --- | --- |
| **会话内工具循环** | agentic 提案**内部** | 调 Lean、读报错、改同一份文件 | `proposal_mode="agentic"` + `max_turns` / `max_tool_calls` |
| **提案格式修补** | 提案层 | preflight 不过时修**格式**，不修证明 | `ProposalConfig.max_repair_rounds` |
| **跨候选 repair lane** | 搜索层 | 取 `latest_failed()` 重来一次 | `SearchConfig.repair_enabled` |

**LEAP Table 5 对应的是第一种。** 而 `BasicSearchProfile` 默认 `proposal_mode="agentic"`，
agentic 会话有 `run` 工具（`ProposalConfig.run_timeout_cap_s` 的注释即指此工具），
`max_turns=48`、`max_tool_calls=120`——**第一种迭代在 `BasicSearchProfile` 里本来就是
开着的**。因此 `repair_enabled=False` ≠「没有编译反馈迭代」。

#### 仍然成立的部分

**横向重组**（两份失败的兄弟证明杂交）没有道理；**跨目标**复用要靠引理库，不靠种群。
LEAP 换掉持久化对象这件事依然对——它保存的是已证引理的集合，其图记忆化消融是直接
证据：只把树换成图让引理跨分支复用，进阶集从 40.0% 涨到 56.7%。

（另记一条 Table 5 确实支持的事实：会话内迭代这个杠杆**只对通用模型成立**——
Gemini-3.1-Pro 从一次性 Pass@128 的 20.0% 升到迭代 Pass@1 的 36.6%，而
Goedel-Prover-V2-32B 从 10.0% 掉到 6.6%。这是本切片用通用模型做后端的依据。）

### 1.4 节点层要成立，适应度必须分级

0/1 的话，节点层确实没东西可爬。做法是**强制候选始终保持在可编译状态**——不会证的
部分用 `sorry` 占位，进度用 sorry 消减来量。这是 LEAP 草图机制的推广，也是人写 Lean
时的实际做法。

```
编译不过                      → 0.0（异常，不是常态）
编译过、还有 sorry            → 按闭合比例给分
sorry-free 但公理不合规       → 拒
sorry-free 且只依赖那三条公理 → 1.0
```

**软适应度只进搜索排序，不建立「证明成立」这个事实。** 这条是
[research_layer.md](research_layer.md) I-6 验收里已经写死的。刷软分的最坏后果是把
搜索带偏，不是把假结论当真——代价有界。

### 1.5 `passed` 的定义决定整套种群机制是不是空转〔承重〕

```python
# evoharness/core/population.py:269
@property
def archive_eligible(self) -> bool:
    return self.passed
```

**只有 `passed` 的候选进档案、进父本采样池。**

若把 `passed` 定义成「完整证明」，则所有部分证明（编译通过、还剩三个 sorry、软适应度
0.6）**永远当不了父本**。分级适应度会被老老实实记下来，然后一次都不被使用；世系只能
靠 `repair` 通道推进，而那条通道走 `latest_failed()`，只取最近一个失败候选，不按适应度
排序。**结果是整套种群机制静默退化成一个串行修复循环，而单元测试全绿**——分桶归档
那次的形状。

**出路在 grader 侧，Core 改动仍然是 0：**

- `passed` = **编译通过**（宽松）→ 部分证明进档案、能当父本、按适应度加权采样
- `solved` = sorry-free + 公理合规 → 由 `criterion.solved_at = 1.0` 与停机机制处理

**适用范围：四级阶梯（§1.6）上全都承重，不只 L3/L4。** L1、L2 用的是
`SeedOnlySelector`，它同样从 `passed_candidates` 里取：

```python
# selection.py:134
seeds = [c for c in island.passed_candidates if c.generation == 0]
```

而种子是**被判过分的**（[loop.py:296](../evoharness/core/loop.py) `seed.report =
self._grade_seed(...)`）。所以若 `passed` 定成「完整证明」，一份 `sorry` 骨架种子就不是
passed → 岛里没有 passed 父本 → `_pick_island` 直接跳过该岛 → **整个 run 一个提案都
产不出来**。比 L3/L4 的退化更彻底：不是变成串行修复，是什么都不跑。

顺带记一条：若走到 L3/L4，跨候选 repair lane 也自动对上——
[operators.py:708](../evoharness/core/operators.py) 的 `build_repair` 会把 `report.fault`
与 stderr 尾部喂回模型，Lean 报错原文正好落在那里。**但这是第三种 repair（§1.3），
不是 LEAP Table 5 那种；主要的编译反馈迭代发生在 agentic 会话内部。**

### 1.6 节点求解器：一个待验证的假设，不是一个决定

> **v2 在这里把结论当成了前提。** v2 写「不用 `BasicSearchProfile`，用
> `EvolutionSearchProfile`」，依据是被误读的 Table 5。v3 把它改回**开放问题**。

**待答问题**：在 Lean 这个域上，**跨候选世系相比会话内迭代还能不能加分？**

现在没有任何证据支持任何一边。而 `EvolutionSearchProfile` 一次会打开六件事——weighted
父本选择、archive、inspiration、novelty gate、跨候选 repair lane、三个算子——把这一坨
的总效应叫「世系继承」，是把六件事记到一件头上。所以 **P-2 改成四级消融阶梯**，每级
只多开一件：

| 级 | 内容 | 怎么表达 | 现状 |
| --- | --- | --- | --- |
| **L1** | 独立 one-shot / best-of-N | `BasicSearchProfile(num_trajectories=N, proposal_mode="single_shot")` | 配置即可 |
| **L2** | **单会话 iterative，最多 K 次 Lean 修订**（= LEAP Table 5 的对应物） | `BasicSearchProfile(num_trajectories=N, proposal_mode="agentic")` | 配置即可。**K 不是一等旋钮**，由 `max_tool_calls` 与提示约束，须在实验记录里写死 |
| **L3** | 跨会话 `latest` 父本继承，**不用 sibling inspiration** | `parent_strategy="latest"`（`_STRATEGIES` 里确有 `LatestSelector`）+ inspiration 计数为 0 | **半通**：`num_archive_inspirations` / `num_top_k_inspirations` 没被 `compile_specs` 透传，`SearchConfig` 默认写死 1/1 |
| **L4** | weighted population（archive + inspiration + novelty 全开） | `EvolutionSearchProfile(parent_strategy="weighted")` | 配置即可 |

**L3 的缺口是唯一需要改代码的地方**：把两个 inspiration 计数加进
`EvolutionSearchProfile` 并在 [compiler.py](../evoharness/runtime/compiler.py) 里透传。
它在 Core **之外**（契约层），但确实破坏了「P-0 到 P-2 零改动」这条性质，如实记在此。

**若最终选 L3 或 L4**，算子侧的配置是：`revise` 主导、`rewrite` 少量、**去掉
`recombine`**（横向杂交那部分原判断仍成立）、`num_islands` 1–2、`migration_rate` 0.0。

**若 L2 与 L4 打平**，节点层就不该用种群机器——回到 `BasicSearchProfile`，但理由与 v1
完全不同：**不是「证明之间没有可继承的东西」，而是「可继承的部分在会话内部已经吃掉
了」**。那种情况下 EvoHarness 在节点层的贡献是图、三态、记账与证据，不是父本选择。

## 2. 角色划分

[dsh_integration.md](dsh_integration.md) 定的「dsh 执行一次 Agent 循环，Python 驱动
搜索与裁决」原样成立，本切片只是把它具体化，并新增第三个角色。

| 角色 | 管什么 | 在本切片里具体是 |
| --- | --- | --- |
| **dsh** | 一次尝试**内部**发生的事 | 模型调用、Lean 编译工具、Mathlib 检索工具、沙箱、会话日志 |
| **EvoHarness Core** | 跨尝试的记账与裁决 | 子目标求解（`api.run`，档次由 §1.6 的阶梯定）、preflight、三态、证据信封 |
| **图控制器（新增）** | 跨尝试的**结构状态** | 已证引理库、目标依赖、总预算、检查点 |
| **Lean** | 正确性 | 编译 + 公理检查，唯一的判定权 |

### 2.1 Python 必须在最外层

[dsh_integration.md](dsh_integration.md) 已经写死：长跑的耐久性不能指望 dsh 的 job
注册表（`jobs-local` 是进程本地的，agent 销毁时会取消并等待 job），**耐久性归
EvoHarness 的检查点；走 SDK 路径时进程树的根就是 Python，这条自动成立**。

一道 Putnam A5 级别的题在 LEAP 那里是 170 个活跃节点、3.0k 次 LLM 调用。这个规模下
必然会崩、会被打断，那时需要恢复的是**整张图**，不是一次 dsh 会话。

**所以图控制器在 Python 一侧、Core 之外，dsh 只出提议。** 环路：

```
Python 图控制器（持有图、预算、检查点）
  ├─ dsh 调用一：Mathlib 检索 + 提议分解  → Lean 草图 + 子目标列表
  ├─ Lean 校验草图 ── 主体 sorry-free，sorry 只在新引理位置 ── 不过就退回
  ├─ dsh 调用二（独立会话）：审稿分解 ────────────────────── 不过就退回
  ├─ 写图（无环性检查 + 引理身份规范化）
  ├─ 每个开放子目标 → api.run(P-2 选出的那一级求解器)
  └─ 回到顶部
```

dsh 承担的三件事——检索、提议分解、审稿分解——**都是「出判断」，不是「持有状态」**。
每件都是一次无状态调用：输入是图的当前快照，输出是一个提议。

### 2.2 图不能住在 dsh 里

若图存在 dsh 的会话上下文里、每轮由模型重写整份，则上下文压缩、会话重启或一次跑偏
的输出都能悄悄把图弄坏或弄丢。而引理跨分支复用正是 LEAP 相对朴素递归的全部增量。

**图是磁盘上的受守卫对象，dsh 通过工具读写。**

## 3. 五个承重点

漏掉任何一个，症状都出现得很晚。

**其一，分解必须被 Lean 校验，不能只被语言模型校验。** LEAP 的分解产出不是自然语言
子目标列表，而是**一份 Lean 草图**：主定理体 sorry-free，`sorry` 只允许出现在新提出
的引理位置，且草图要编译通过才能作为 AND 节点提交。这条保证「子目标全部证完，父目标
自动成立」。省掉它会得到一堆**各自都证明了、但拼不回原命题**的引理，而且图上一片绿
时才发现。

**其二，审稿必须是独立的一次调用。** LEAP 去掉审稿人后，智能体会先展开定义造一个
中间引理、再折叠回去，提出一个**和祖父目标逐字相同**的子目标——形式合法、Lean 也认，
但实质原地踏步，八次 rollout 全烧光。Aletheia 那边的观察指向同一件事：把最终输出与
中间思考 token 拆开，模型才认得出自己生成时没看见的漏洞。**同一次会话里让模型审自己
刚写的分解等于没审。**

**其三，图是带 schema 的外部对象。** 两道写入守卫：无环性检查（LEAP 的 state writer
就干这个）；引理身份哈希——同一条引理改个名字不能在图上变成两个节点，否则记忆化白做。
**范围与失败方向见 P-3 的 3b：只做 elaborated 表达式的 alpha/definitional 哈希，
哈希失败时倒向「不是同一个」。**

**其四，预算得有人扣。** `BudgetMeter` 的 `state_path` 是 `run_dir/budget.json`，
**一 run 一本账**。170 个节点就是 170 本互不相关的账，图层自己的调用还完全不在账上。
**总账由图控制器持有，每次调用前先扣。** 这也是 Python 该在最外层的另一个理由。

**其五，根目标的凭据是组装后的整体复验，不是逐节点的绿灯。** 见 P-3 的 3d。

### 4.1 实跑记录（2026-08-28，gpt-5.6-sol）

链路端到端通过，**两次跑，两条不同的路径**：

#### 3a. 三类对象与三套状态〔承重契约〕

> v1–v3 的 P-3 只写了「图存储、无环、三态」，**不足以表达 AND-OR DAG**。v4 补齐。

```
Goal
  ├─ OR → Decomposition A
  │          ├─ AND → Subgoal 1
  │          └─ AND → Subgoal 2
  └─ OR → Decomposition B
             └─ AND → Subgoal 3

Goal
  └─ Attempts：每次直接证明 / 修复的运行结果
```

**三套状态必须分开，不能压成一套：**

```
Goal.status           open | proved | exhausted
Decomposition.status  proposed | accepted | rejected-by-verifier
                               | rejected-by-reviewer | completed
Attempt.outcome       proved | task-failed | budget-exhausted
                             | timeout | infra-failed | interrupted
```

- [x] **`infra-failed` 是一次 attempt 的结果，不是节点终态。** 它绝不能让图把该子目标
      标记成「此路不通」然后去换分解——那是「基础设施故障被当成能力退步」的翻版，
      在这里后果更贵：它会让整张图朝错误方向重构。
- [x] **`Attempt` 就是一次 `api.run()`**，对应一个 run 目录 + manifest + `EvidenceEnvelope`。
      `outcome` **必须从 run 报告派生，不得由图控制器另写一遍**——否则「这次试成了没有」
      有两个真相源。现成映射：

  | `RunReport.stopped_reason` | → `Attempt.outcome` |
  | --- | --- |
  | `target_reached` | `proved` |
  | `completed`（fitness < 1.0） | `task-failed` |
  | `eval_infra` / `proposer_dead` | `infra-failed` |
  | `budget` / `llm_billing` | `budget-exhausted` |
  | manifest 未 finalize（`running`） | `interrupted` |

  **只有 `task-failed` 是关于能力的证据，其余全是关于这次运行的证据。**
  `budget-exhausted` 必须与 `task-failed` 分开：前者加预算重跑可能就成，后者才是能力信号。
- [x] **`Decomposition` 的两种 `rejected` 必须分来源。** `rejected-by-verifier` 是 Lean 说
      草图不合法——事实，不该重访；`rejected-by-reviewer` 是审稿人说这个分解没用——
      **启发式判断，可能错，必须可重访**（换预算、换审稿人提示、或别的路都走死后回来）。
      压成一个 `rejected` 会让 §1.2 那条线（模型判方向、不判对错）在实现里消失。
- [x] **`Goal.exhausted` 是预算相对的**，必须记下在什么预算、什么求解器档次下穷尽。
      否则加预算 resume 时没有依据重开它，图会永远绕着那个节点走。
- [x] **并发租约不进 `status`。** `Goal.status` 保持三值纯语义；「谁正在攻这个目标」
      放单独的 lease 字段。L1/L2 可并行，图层一定会并发攻多个开放目标，但那是调度状态。
      把 `in-progress` 塞进 `status`，半年后会看到 `in-progress-retrying`、
      `stale-in-progress` 并存。

#### 3b. 身份哈希：范围与失败方向〔承重〕

- [x] **只承诺对 elaborated Lean expression 做 alpha-normalization / definitional identity
      hash。不承诺识别逻辑等价命题**——那通常不可判定。
- [x] **这个哈希本身是一次 Lean 调用**（要拿 elaborated 表达式就得跑 elaborator），
      因此会失败：超时、Mathlib 报错、依赖没编。
- [x] **失败时必须倒向「不是同一个」，绝不能倒向「是同一个」。** 错误合并会让一个
      未证目标继承另一个目标的已证状态——**这是本切片里唯一能直接产出假结论的路径**。
- [x] **代价不对称，写在正文里挡住后人**：漏合并只损失效率（少一次复用），错合并
      损失正确性。**因此禁止用 LLM 判定引理等价来「提高复用率」**——那是个很自然、
      很诱人的后续改进，而它会把上面这条护栏整个拆掉。

#### 3c. 其余骨架

- [x] 图存储：带 schema 的外部对象（SQLite 或 JSONL），不是上下文里的一段 JSON。
- [x] 写入守卫：无环性检查 + 3b 的身份哈希。
- [x] 跨 run 总预算账本（承重点其四）。
- [x] 整张图可检查点、可恢复。`interrupted` 是唯一**可续**的 attempt outcome
      （run 目录本身带检查点），其余都是终态。
- [x] 每个子目标是**动态生成的 TaskSpec**（Lean 命题不同 → task hash 不同）。契约上
      干净，但要为每个子目标物化一个种子目录（放一份带 `sorry` 的骨架）；现在
      `ResolvedTask.from_directory` 是从目录构建的，这几十行要写。
- [x] 建一个「图节点 → run 目录」的索引。170 个节点就是 170 个目录 170 个 `run.db`，
      没有索引事后无法审计。

#### 3d. 最终整体复验〔承重〕

- [x] **`Decomposition.completed → Goal.proved` 这条传播不得以逐节点绿灯收尾。**
      引理是在 N 个独立 run 目录里、跨很长时间分别证出来的；凑齐时 Mathlib 版本、
      兄弟引理签名、`sorry` 填法都可能已经漂了。
- [x] **根目标被证明的凭据，是组装后整份文件完整编译通过 + 公理检查通过。**
      草图校验挡的是分解错误，这一道挡的是**装配漂移**。

#### 3e. 用桩求解器建图，不接模型也不调 `api.run()`

> **v5 收紧。** v4 写的是「先不接模型，人工分解，让图去调 `api.run()` 逐个攻」——
> 还不够。真正该桩掉的是**子目标求解本身**。

- [x] **每个子目标由一个桩返回一份预写好的证明**（fixture 的三条引理各配一份）。
      这样 AND-OR 传播、三套状态、身份哈希、装配复验、崩溃恢复**全部可以确定性地测**，
      跑一遍几秒钟，一次模型调用都不花。
- [x] 桩要能按剧本返回**每一种 `Attempt.outcome`**——尤其 `infra-failed` 与
      `interrupted`，否则那两条最重要的路径根本没被走过。
- [x] 图跑对之后，再把桩换成真的 `api.run()`（节点求解器暂用 L2，见 §4 开头的空缺表）。

**验收**：fixture 端到端通过——**子目标全绿、组装后整体复验也绿**；杀掉进程再恢复，
图状态完整且 `interrupted` 的那个 attempt 能续上；**桩注入一次 `infra-failed`，确认它
没有把任何 `Goal` 推向 `exhausted`、也没有触发换分解**；桩注入两条 alpha-等价但写法
不同的引理，确认被合并；注入一次身份哈希失败，确认**没有**被合并。

**为什么不能跳过**：先验证图的语义、再接模型。跳过的话，P-4 的失败会分不清是分解
质量差还是图本身接错了。

### P-5 · 中间档上的完整闭环

- [ ] 用 P-2 的表选题，只打中间那一档。**P-0c、P-1、P-2 必须在此之前补齐。**
- [ ] 两条臂，**同预算**，且两臂的节点求解器必须是 **P-2 选定的同一级**：

      **有图**：图分解 + 每节点跑同一级求解器。
      两臂之差**才是图分解本身的价值**。若两臂用了不同档次的求解器，求解器强度的

- [ ] **报告逐题配对结果，不报总分差。** 30 道题上 ±2.6 道的噪声会把两三道题的真实

      `evoplus/behavior.py` 的 `SignatureRecorder` 通过/失败签名正好是这个用途。
- [ ] 跑完过一遍 `scripts/audit.py`，确认**引理复用次数大于零**。若图记忆化全程没复用
      过任何引理，那它就是棵树，LEAP 那 40.0% → 56.7% 的增量一分都没拿到——**而单元
      测试不会告诉你这件事**（参见字节预算那轮：分桶归档全程未生效、ledger 静默，测试全绿）。

**验收**：能给出一份逐题配对表，说明图分解在哪几道题上翻盘、在哪几道题上更差。

## 5. 风险登记

| 风险 | 在哪一步暴露 | 对策 |
| --- | --- | --- |
| Lean 编译墙（编译次数而非模型调用是瓶颈） | P-1 | 闸门判据，超了就砍掉 P-6 |
| 分解拼不回父目标 | P-3 手工分解 | 先验证语义再接模型；草图必须过 Lean |
| 噪声吞掉信号 | P-2 实测 | 逐题配对比较，不比总分 |
| 机制空转（图退化成树） | P-5 | `audit.py` 查引理复用次数 |
| **机制空转（种群退化成串行修复）** | P-2 空转检查 | `passed` = 编译通过（§1.5）；确认带 sorry 的父本被采样过 |
| **归因错误：把一坨机制的总效应记到其中一件头上** | P-2 阶梯、P-5 双臂 | 一次只跨一格；两臂求解器同级。**本文档 v1、v2 各犯过一次** |
| **离线 demo 结构上够不到某些路径** | P-3 实跑 | 脚本化的模型总走同一条路；真模型走了另一条，两个 bug 才现形。**桩测的是机制，不是覆盖** |
| **`repair` 一词歧义导致误判开关** | 设计期 | §1.3 的三分表；`repair_enabled=False` ≠ 无编译反馈迭代 |
| **软适应度被刷（削弱命题、sorry 外逃）** | P-0a 验收 | 编辑区标记锁死 `theorem` 语句；公理检查；软分只进排序不建立事实 |
| 基础设施故障被当能力退步 | P-3 验收注入 | `infra-failed` 是 attempt 结果，不是 `Goal` 终态；不触发重新分解 |
| **错误合并两条不同引理 → 未证目标被标成已证** | P-3 身份哈希 | 哈希失败倒向「不同」；**禁止用 LLM 判等价** |
| **装配漂移：逐节点全绿但组装不起来** | P-3 最终整体复验 | 根目标凭据是组装后整体编译 + 公理检查 |
| **`budget-exhausted` 混进 `task-failed` 污染能力统计** | P-3 outcome 派生 | outcome 从 `stopped_reason` 派生，不由图控制器另写 |
| **把求解器强度的功劳记到图头上** | P-5 双臂 | 两臂的节点求解器必须是 P-2 选定的同一级 |
| Basic 集看起来「已饱和」而误判 | P-2（推迟） | 种子约 11/30、天花板 25/30，空间是实的；「饱和」只对**一次性生成**成立 |

## 6. 依赖线与停止线

```
P-0a ✅ → P-3 ✅ → P-0b ⬅ 现在这里 → P-4 审稿人 → 〔P-0c + P-1 闸门 + P-2 阶梯〕→ P-5 → P-6
                    ↑ 阻塞在 Mathlib 工程
```

**P-4 的求解器与分解源已提前落地**（见该节），所以 P-0b 之后要补的只有审稿人。

**机制侧（不需要 benchmark）**

- P-0a 未完成：不得开写图代码——草图校验与最终整体复验都要真 Lean；
- **P-0a 的「带 sorry 候选可进档案」验收未过：不得往下走**。这个布尔值错了，L1/L2 一个
  提案都产不出来，L3/L4 静默退化成串行修复；
- P-3 未完成（桩求解器未跑通、或最终整体复验未接）：不得接模型分解；
- **P-3 的身份哈希失败方向未钉死：不得启用引理复用**——宁可全程不复用，也不能错合并；
- P-0b 未完成：不得跑 P-4 的审稿人消融（fixture 太简单，退化模式不会出现）；
- P-4 的审稿人消融未复现退化：不得相信审稿人已接上。

**benchmark 侧（推迟，但在 P-5 之前必须补齐）**

- **P-1 未放行：不得开工 P-6**；
- **P-2 的阶梯未跑完：不得选定节点求解器**，也不得声称任何一级「有用」或「没用」。
  P-3、P-4 期间用的 L2 是**未经验证的默认选择**，不是结论；
- P-0c 未完成：不得选 P-5 的题，因为不知道中间档在哪；
- P-5 未完成：不得开工 P-6；
- 任一阶段都不能以「模型认为证明了」代替 Lean 判定。

## 7. 三条贯穿规则

1. **P-0a 到 P-4 的 Core 改动是 0**（P-2 的 L3 需要一处契约层透传，仍不动 Core）。
   机制侧全部可以在 fixture 与三五道真题上做完，不受成本闸门影响；**成本墙在 P-5 才撞上**。
2. **每步之前先跑 `scripts/audit.py`**，别让「机制没生效」伪装成「机制没用」。
3. **不合并步骤。** 尤其 P-3 的桩求解器看着可以跳过，跳过之后 P-4 的失败无法归因。
